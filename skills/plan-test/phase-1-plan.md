# Phase 1 — 调查与写 plan

**目的**：基于 `{ACCEPTANCE_FILE}` 的矛盾分析，先调查、再实践、后写出一份**代码级可执行**的 plan。铁律：**没有调查，就没有发言权**——plan 里每个"现状"论断必须来自本次真读过的代码，每个关键假设必须来自真跑过的实践。

## 步骤

1. **调查现状（原架构基线阶段并入此处——调查为写 plan 服务，不产出独立架构文档）**
   - **围绕主要矛盾圈定调查范围**：主要矛盾的解法会触碰哪些模块/调用链/外部依赖，就调查哪些；与解法无关的部分不通读（调查深度向矛盾的主要方面倾斜）。
   - **解剖麻雀**：对最核心的改动模式，选一条典型调用链从入口挖到底（入口 → 路由 → 服务 → 持久化/外部调用），结论写成通用模式供同类改动点引用。
   - 调查结论**直接写进 plan 的"现状"栏与文件影响清单**，论断附代码证据（文件:行号）；不维护独立的 ARCHITECTURE.md（项目自己维护架构文档的，收尾时顺手更新，见 phase-final）。
   - 调查纪律遵循 `methods/research-method.md`。
   - 调查发现需求技术上不可行、或与 acceptance 严重冲突 → 标记 BLOCKED 升级，不硬写 plan。

2. **最佳实践调研（不可跳过）**
   - 针对主要矛盾的解法方向，调研业界最佳实践怎么解决。
   - **反对本本主义**：每个外部方案必须附"本项目适配分析"（该实践的前提条件、本项目条件哪里同哪里不同、照用/改造/不用）；只写"业界都这么做"视为未完成。
   - 把"为什么选这个方案、放弃了哪些备选、权衡是什么"写进 plan。

3. **实践先行（不确定的当场实践，不等 challenger 逼问）**
   - 列**关键假设清单**："决定方案成败、且静态阅读无法确认"的假设——三方库/API 真实能力、LLM 输出契约、数据源真实形态、性能可达性、关键链路运行时行为。局部细节不算，别撑成全量测试。
   - 每条关键假设**当场写可丢弃 spike 真跑验证**（真实调用/真实数据/真实 provider），命令 + 实际输出记入 plan 的"关键假设与实践证据"节。**"读过源码应该支持 / 理论上可行"不算数。**
   - 假设不成立 → 方案层面改（必要时回 phase-A 和用户重新讨论方向），不许硬着头皮往下写。
   - spike 代码即弃，不滚成实现（`SELF_BUILT_DEFENSE: forbidden` 同样适用于 spike——用现成工具验证，不为验证造系统）。

4. **写 plan，细到代码级**
   - 存放：`{PLANS_DIR}/<按需求命名的新文件夹>/plan.md`。
   - 每个改动点必须明确：**改哪个文件 → 哪段/哪个函数 → 怎么改 → 改成什么样**。
   - 把 plan 切成可独立执行、可独立验证的"咬一口大小"的任务；每个任务标注它满足哪条 AC 及该 AC 的**矛盾地位**（决定性/次要）。
   - **任务排序 = 最短价值路径优先**：在依赖合法的前提下，最先到达"价值验证里程碑"（acceptance 声明的最小验证动作）的路径优先；里程碑之前只许排它的直接依赖，加固性/次要 AC 的任务一律排在里程碑之后。禁止用"按依赖排序"作为把仪式性任务排到价值点之前的理由。
   - 填写 `Complexity inventory`：每个新增复杂度表面必须绑定 AC 或范围内风险；无绑定项会在 phase-2 收敛后的 minimality pass 中删除（统一规则见 `policies/acceptance-preserving-ponytail.md`）。
   - 明确列出入口链、数据流/持久化、外部依赖与停止追踪点；FULL 路径把已知假设绑定 `assurance-contract.json` 的稳定 ID。

5. **铁律**
   - `BEHAVIOR_POLICY = preserve-approved`：不得静默减少用户已批准的外部行为；内部实现可删可换可重构。
   - "100% 代码可执行"只表示：对用户批准的 required AC 和已知证据，所有条款都有确定实现与验证出口；不表示未来零缺陷。

## plan.md 建议结构

```markdown
# Plan：<需求名>

## 矛盾分析（从 acceptance 复述并深化）
- 主要矛盾 / 主要方面：……
- 最小验证动作：……
- 价值验证里程碑：Task N（里程碑之前只许排它的直接依赖）

## 现状调查结论
- 相关模块与调用链（麻雀解剖结果，附文件:行号证据）：……
- 现有实现方式与技术债：……

## 方案与权衡
- 选定方案 / 放弃的备选 / 本项目适配分析：……

## 关键假设与实践证据
| 假设 | 验证方式（spike 命令） | 实际输出 | 结论 |
|------|----------------------|----------|------|

## 关联验收标准
- 覆盖 AC-1（决定性）, AC-2（次要）, …（每条都要有任务覆盖）

## 文件影响清单
| 文件 | 职责 | 现状 | 本次改动 |
|------|------|------|----------|

## Complexity inventory
| 复杂度表面 | 本次是否新增 | 理由 / AC 或 risk 绑定 |
|-----------|:---:|-----------------------|

## 任务清单（最短价值路径优先）
### Task 1 — <标题>  [覆盖 AC-1（决定性）]
- 改动文件：path/to/file
- 现状：（本次真读过的当前实现）
- 修改方式：（代码级，怎么改）
- 验证：（怎么测这一步——先写"什么算对"，oracle 先于实现）
- 依赖：Task X
```

## 出口

- plan 覆盖全部"必须" AC、每个任务到代码级、关键假设全部有 spike 实测证据 → 进入 phase-2 迭代。
