# Phase 1 — 写 plan

**目的**：基于 `{ARCH_DIR}/ARCHITECTURE.md` 与 `{ACCEPTANCE_FILE}`，写出一份**代码级可执行**的优化/升级 plan。

## 步骤

1. **最佳实践调研**（不可跳过，纪律见 `methods/research-method.md`）
   - **先抓主要矛盾**：调研第一步先回答"这个需求里决定成败的核心问题是哪一个"，写进 plan 开头，调研深度向它倾斜。
   - **主要矛盾的格式硬约束**（2026-08-31 DGX 复盘：两份 plan 一份写成八个目标的合集、一份把防御排第一优先，全都没被任何环节发现）：
     * **单一矛盾**：一句话只许一个核心问题。写成"A+B+C+D 同时成立"的复合句 = 没写，challenger 必须打回；
     * **价值在前，防御在后**：主要矛盾必须是"用户要的核心价值能不能成立"（如"304B 模型能否在两台机上 TP=2 出 token"），不许把边界/诚实性/防御性关切写成第一优先——那些是价值成立之后的次要矛盾；
     * **附最小验证动作**：一并写出"用最小代价证明它成立的那一步"（一条命令、一次请求、一个最短调用链），这一步就是任务清单里的**价值验证里程碑**。
   - 针对需求里的每个问题，调研业界最佳实践该怎么解决。
   - **反对本本主义**：每个外部方案必须附"本项目适配分析"（该实践的前提条件、本项目条件哪里同哪里不同、照用/改造/不用）；只写"业界都这么做"视为未完成。
   - 把"为什么选这个方案、放弃了哪些备选、权衡是什么"写进 plan。
   - 对最核心的改动模式**解剖麻雀**：选一条典型调用链从入口挖到底，结论写成通用模式供同类改动点引用。

2. **写 plan，细到代码级**
   - 存放：`{PLANS_DIR}/<按需求命名的新文件夹>/plan.md`。
   - 每个改动点必须明确：**改哪个文件 → 哪段/哪个函数 → 怎么改 → 改成什么样**。
   - 把 plan 切成可独立执行、可独立验证的"咬一口大小"的任务。
   - 每个任务标注它满足 `{ACCEPTANCE_FILE}` 里的哪条 AC（建立可追溯链的起点）。
   - 填写下方 `Complexity inventory`：每个新增复杂度表面必须绑定 AC 或范围内风险；
     无绑定项会在 phase-2 收敛后的 minimality pass 中删除。统一规则见
     `policies/acceptance-preserving-ponytail.md`。
   - 明确列出入口链、数据流/持久化、外部依赖、可信边界和停止追踪点；安全敏感任务在首次
     challenger 前完成 attack-surface inventory。
   - 把已知假设绑定 `assurance-contract.json` 的稳定 ID；不在当前 contract 内的新要求只能写成
     scope-change proposal，不能直接纳入 required plan。

3. **铁律**
   - `BEHAVIOR_POLICY = preserve-approved`：不得静默减少用户已批准的外部行为；内部实现可删除、
     替换或重构，acceptance 明确批准删除的旧行为可以删除。
   - 必须含**实现细节调研**结论，不只是"做什么"。
   - "100% 代码可执行"只表示：对用户批准的 required AC、assurance contract 和已知证据，
     所有条款都有确定实现与验证出口；不表示未来零缺陷或抵御任意未批准攻击者。

```markdown

- 最小验证动作（用最小代价证明它成立的那一步）：……
- 价值验证里程碑：Task N（里程碑之前只许排它的直接依赖）

## Complexity inventory

| 新依赖 | 否 | — |
| 新公共 API | 否 | — |
| 新持久化状态 | 否 | — |
```
