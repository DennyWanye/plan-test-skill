# 按可交付能力切片

三个入口规划或执行 delivery 任务时读取。与 `user-attention.md` 配合：切片是 Agent 的交付单位，不是新增用户批准点；本规则不新增机器门或扩大操作授权。OPS 继续使用原运维路径，按目标服务状态分阶段，不强套代码提交模板。

## 整体计划 → 交付切片 → 技术任务

- **整体计划**固定用户目标、全部 MUST AC、行为/预算/风险边界、目标架构和切片依赖。每条 MUST 都有负责切片，跨片能力写清最终组合验证；未执行项始终保留，不能靠拆片消失。
- **交付切片**在前面已验证的产物上增加一项可用能力。用这个问题审查：后续暂时不做，当前累计产物是否仍能通过一个实际入口使用并验证它承诺的用途？独立验收不等于脱离所有前序依赖重新运行。
- **技术任务**是文件/模块级步骤，放在切片内部。建表、加接口、接 UI 可以是必要任务；只完成其中一层，通常不能称为交付切片。必要底层准备归入最早消费它的切片，不另造“准备完毕=交付成功”。
- 小需求可以只有一片，不设最少片数。体量上限用于发现过大片，不定义切片质量。沿目标架构扩展已有能力，不为了模仿“滑板到汽车”反复重写系统。

## 每片交付表（写进现有 plan）

| 字段 | 内容 |
|---|---|
| ID / 新增能力 / AC | 使用者完成什么，覆盖哪些原始验收条款；只覆盖某 AC 一部分时写出本片断言与最终负责片 |
| 产物与真实入口 | 可运行代码/构建/命令/API/库调用，怎样从输入到可观察结果；明确运行环境 |
| 最小决定性验证 | 实现前写好输入、独立预期与通过条件；包括该能力必需的安全性和正确性 |
| 前序依赖与边界 | 哪些已交付能力是前提，本片承诺到哪里；外部资源和操作授权是否具备 |
| 保留能力与回退 | 前片哪些行为必须继续成立、受影响回归、失败后怎样安全恢复 |

真实入口随交付对象而定：应用从用户界面，CLI 从实际命令，API 从真实请求，库/SDK 从真实消费者或可执行集成样例进入。库本身就是用户要求的交付物时不强造 UI；仅 mock、内部函数自测或流程 completed 不足以证明声明的可用能力。最终目标要求真实 provider/设备时，替身验证只能算准备证据，不能冒充该目标的交付。

## 逐片细化，提前验证整体风险

整体成败依赖的假设（架构选型、数据/迁移可行性、外部能力、重大成本、跨片接口约束）先调查，静态资料不足则做最小 spike；不能标为“后续再研究”就宣称整体方案可行。

整体计划确定各片能力、依赖和验收后，**当前片**完成代码级调查、任务、oracle 与挑战闭环，再实施。**未来片**允许暂不写易过时的函数级细节，但必须标明待细化项、触发时点与风险，不写成已验证/可直接执行。进入下一片前由 Agent 补调查、spike、挑战与基线差异检查；范围内技术细化不重新索取批准。

单片 `plan.md` 可以沿用现有 finalized 标记；多片 program 的总体方案定稿不代表未来片已具备开工条件。以 plan 内明确的当前片和开工检查为准。超过体量上限时用 program 总览关联各独立交付片的执行 plan；总览保留全 AC 映射。体量机检按实际 release unit：同一 run 内分片不缩小原 run 的计数或阈值；独立片 run 才按该片完整范围计数。不压缩数字、改 MUST 或隐藏全局风险。

## 每片执行闭环

1. 核对该片前序产物、授权、风险与开工前提；跨片依赖尚未通过则不启动依赖实现。
2. 完成到真实入口的最短链路及必要控制，实际运行本片最小决定性验证。
3. 按影响范围验证本片其余承诺、保留能力及必要回归；修复失败或走 A2，不能靠开始下一片掩盖未交付状态。无依赖的已授权调查可继续，不把它算新片交付。
4. 按适用风险完成 review/审计，保留可追溯提交与被测内容身份；允许片内有多个工作提交，但必须有一个完整接线、可验证的片终点。提交后按既有内容身份规则确认测试与交付内容一致。
5. 记录能力、真实入口、测试结果、提交/构建身份及限制，异步展示实物。当前片验收闭环后，自主细化并推进下一片；用户要求暂停/验收或实际越出授权时，按注意力规则处理。

## 片验收与整体完成

**先确定验收范围与 run 的对应关系，不能执行到一半随意切换：**

- **同一交付 run 内分片**：该 run 的 acceptance/contract、required 场景仍覆盖原声明范围。每片在原账本追加真实结果，未来项保留 NOT_RUN。片的能力验收、适用 review、回归与提交身份核对后，记“SL-x 里程碑通过，整体未完成”并推进下片；此时不要求整个 run 的 READY_FOR_AUDIT/finalize，也不产生片 receipt。phase-4/final 中这些整体条件等全部 required 及组合验证完成后执行。既有整体 frozen run 默认沿此路径继续，不通过改 required/重开 run 适配新规则。
- **各片独立交付 run**：适用于需独立交付或超体量上限的 program，在开账前选定。总览保留全部原始 AC 和依赖；每片执行 plan + slice acceptance/contract 映射原始请求、本片断言及继承的全局风险。本片验收与 oracle 准备就绪后，机器门路径先按 `evidence-audit-lifecycle.md` compile/init，再按 phase-2 start-challenge-loop 完成挑战、关键假设验证与定稿，全部在实现前完成；冻结后发现需改 contract/oracle 走原机制。该片适用的审计/finalize 成功才算该片独立交付。未来片不提前伪造冻结 oracle，开工前同样完成准备。已冻结 run 的 scope/contract 变化仍按原批准机制，不可用新片丢弃旧义务。
- **无机器门的路径**：以同样明确的片承诺和全局映射记 journal，不为每片新增 ledger/receipt。是否使用机器门取决于实际风险及项目要求，不能用片数决定或降级。

每片复用现有 phase-2/3/4 的必要动作，证据记在现有 plan/journal/testcase 中。整体未变的调查、批准、基线和昂贵测试按原内容身份/变更影响规则复用；不要给每个小片无条件套完整大项目仪式。命中机器门、真实 UI/provider 验证等既有要求时照常执行，不能因“小片”降级。

审阅、验收、报告都明确当前作用域：可以说“SL-1 验收通过，整体尚有 SL-2/3”；不得把当前片 PASS 写成整个需求完成。拆成独立交付 run 时，保留原请求与全局 AC 映射，slice acceptance 说明原需求中本片的断言与外部约束；它不能反写或削减整体 acceptance、降低继承的风险边界，既有冻结 contract 不静默改写。

整体收尾核对全部原始 MUST AC、跨片组合能力与累计回归；各片单独 PASS 不能代替必要的组合验证。每片可交付不等于每片都必须部署生产，发布仍按原授权和风险要求办理。
