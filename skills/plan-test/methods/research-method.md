# 调研方法论 — 毛选式问题解决

phase-1（现状调查 + 最佳实践调研）、phase-2（迭代补充调研）共用的调研纪律。调研类步骤开始前先过一遍本清单；plan-challenger 会按这些条目反向执法。

需要用户决策时，先做围绕该选择的定向调查并整理决策简报（`../references/user-attention.md`，RULES R11）；已有事实足以比较选项就停。缺失的是用户目标或权限时直接说明缺口，不无限调研。

## 1. 没有调查，就没有发言权
- plan / 架构文档里**每个论断必须附代码证据**（file:line 或命令输出），禁止"我认为应该是""一般来说是"。
- 没读过的代码不许下结论；来不及读的，标为"未调查项"进待闭环清单，不许写成结论。

## 2. 抓主要矛盾
- 调研的第一步**不是罗列所有问题**，而是回答：决定成败的核心问题是哪一个？
- 写进 plan 开头（"主要矛盾：……"），调研资源优先砸向它；次要问题跟着主要矛盾的解法走，不单独展开。
- 主要矛盾判断允许在迭代中被挑战者推翻重来。

## 3. 具体问题具体分析（反对本本主义）
- 引用外部方案必须写：该实践成立的前提；本项目条件（规模、依赖、团队、存量代码）哪里同、哪里不同；照用 / 改造后用（改造点）/ 不用。
- 只贴"业界都这么做"而无本项目适配分析的调研结论，视为未完成（phase-1 步骤 2）。

## 4. 解剖麻雀
- 不对十个模块浅调研：选一条典型调用链从入口挖到落库，吃透再推广（phase-1 步骤 1）。
- 麻雀选最能代表本次改动模式的那条链路（同类里最复杂或最常见）。
- 结论写成通用模式，其余同类改动点引用该模式即可，不逐个深挖。

## 5. 实践—认识—再实践
- 读代码读不出的不确定项（运行时行为、性能、三方库真实表现）允许用小 spike 闭环，结论写回 plan；spike 是调研手段，不许把 spike 代码直接滚成实现（phase-1 步骤 3）。
- 每轮挑战暴露的认识盲区，用新一轮调研闭环，而不是用措辞圆过去。

## 6. 集中优势兵力，各个歼灭
- 并行派子代理调研时，**多个代理集中攻坚最难的那一个不确定项**，各从不同角度切入（读实现 / 读调用方 / 跑 spike），不平均分块。
- 歼灭一个再打下一个；一次并行只围一个歼灭目标。

## 7. 打歼灭战，不打击溃战（根治，不补丁）
- 真架构问题（职责错位、边界穿透、循环依赖、抽象缺失）→ **按最佳实践从结构上根治**，不许用 hack / 特例分支 / 复制粘贴击溃。
- 判定要有证据、讲分寸：根因确在结构层、补丁会留技术债、同类问题会复发才算；不把局部实现问题夸大成架构问题过度重写。
- 重构范围显著超出原需求 → 摆"补丁 vs 重构"的代价对比，交用户拍板，不闷头自决。
- 落地细节见 `phase-2-iterate-plan.md`"强约束：真架构问题优先重构"。

## 调研产出自查（收尾前逐条自问）
- [ ] 主要矛盾已明确写出，调研深度与之匹配？
- [ ] 每个论断有 file:line 或命令输出证据？
- [ ] 外部最佳实践都有"本项目适配分析"？
- [ ] 至少解剖了一只麻雀？
- [ ] 剩余不确定项都有闭环手段（继续读 / spike / 问用户），而非模糊收尾？
