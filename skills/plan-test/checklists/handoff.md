# 交接检查单（`HANDOFF_CHECK`）

**什么算交接**：RULES R10 四问（①让用户动手 ②要用户表态 ③说完成/通过/可推送或断言 ④停下等用户）任一为是，拿不准就当是；本文件是 H0–H4 的条文细则。

| 消息里有 | 做什么 |
|---|---|
| ① 或 ③ | 过 H1、H2、H3 + **完整评估** PASS 才发 |
| 只有 ② 或 ④ | 过 H3 + **轻量评估** PASS 才发（决策依据的事实断言要附来源） |
| 都没有（纯进度汇报、开放式澄清） | 自查 H3 自问句与 H4 |

DIRECT 同样按上表。

## H0 消息结构：把"要你做什么"放在开头

1. **第一段先写需要用户做什么**：要么编号列出待决项（每项按 H3 三段写），要么明写"不需要你做任何事，这条只是汇报"。不许让用户读完全文才发现要决策。
2. **待决项在前，过程与证据在后**：结论、要用户做的事、下一步，排在做了什么、怎么验证的、挑战过程之前。
3. **隐含待决点必须显形**：消息里出现执行入口、命令、"你也可以…""随时可以…""要改也可以"时，写明这是"给你参考、不用回"还是"要你现在定"；后者编号进待决清单。

## H1 需求没做少

宣布完成前，拿交付的真实界面/入口逐条对照 acceptance 的「原话对照」表（phase-A 建表），看原话不看 AC 措辞；原话写了"在哪里"就必须在那里；原话里的质量要求（简洁明了、看得懂、说明原因）要用截图对照，不能只凭代码判兑现。对不上且没有用户批准记录 = 做少，不能交。

## H2 自测到位

1. **真点**：用户看得到的界面改动，自己在浏览器里真实点击、输入走完（首选 harness 内置浏览器，其次 Chrome MCP）。脚本（`javascript_tool`/`$wire`/`dispatchEvent`/直调接口）只能读状态或造前置数据，不能代替点击。点不了 → BLOCKED，按 H3 请用户批准等价方案；未经批准的"如实说明没真点"不是出口。命令行工具的交付，在终端跑用户会敲的命令即算真点。
2. **每个新增或改动的按钮/链接/表单**：点下去有看得见的反馈；每个等待、空、失败状态都有出路。
3. **真实数据**：至少走一条真实数据路径；模拟开关、测试 fixture 跑通不代替真实情况。
4. **已知问题清零**：自测发现的用户可见问题（含文案、报错提示）修掉并复测；修不了的进 H3 决策，不能带着已知问题叫用户测。
5. **消息写清验收路径**：从哪里进、用什么账号和数据、点哪几步、应该看到什么。

## H3 决策讲清

每个待决项写成三段，多个编号攒成一条消息；正文里顺带要用户表态的事也必须编号列入：
1. **要决定什么**：一句话 + 一个用户在界面/数据里看得到的具体例子。出现内部名词（字段名、key、分支名、命令、代号）必须写清两件事：用户在哪个页面/文件的哪一栏看到它，以及它影响什么。附上已查明的事实（注明哪些是推断）与剩余未知。
2. **选项**：只列真实可选的；每项写选了之后用户会看到什么变化、代价、能不能改回。
3. **我的默认**：推荐哪个、为什么；不回复会怎样、是否卡住当前工作。

发出前自问：**用户不打开任何文件、不懂代码，只看这条消息，能不能直接回"1A 2B"？**
最常见的不能：内部名词没说在哪看到、只有统计数字没有具体例子、夹带的待决项没写"你不回我就按 X 做"。

## 评估与出口（流程见 RULES R10 交接卡，此处只放细则）

- 评估员是只读子代理：prompt 给 `prompts/test-result-evaluator.md` 路径（评估员自读）+ `MODE: full|light` + `ROUND: n` + 上下文包；每交接点最多 `HANDOFF_EVAL_MAX_ROUNDS` 轮，两轮 open block ID 不变且无新证据即早停。
- 改写纪律：不许把消息越改越长——先删技术细节和内部流程名词，再补用户要的例子；改完长度不超过原草稿的 1.5 倍。
- finding ID 重复或与上一轮冲突 → 去重后按最严处理（block 优先于 note）。
- BLOCKED 升级消息末行写 `交接评估：FAIL（评估文件名）`。

## H4 通用

- 用用户使用的语言回复；给子代理的 prompt 同样用这种语言。
- 消息涉及生产环境时，第一句标明本次对生产是只读还是写入。
