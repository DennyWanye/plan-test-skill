## 八项证据与解释

### 1. 已有批准应跨阶段和续接保留

**证据**：R3 第 1729 行，09-05 09:01:06 +08，v0.7.2。用户说：“我批准你进行，另外，我不喜欢你把token和资源浪费在反复的确认上”。第 1734 行，Agent 将批准明确绑定到已提出的 SDK 限定解冻和 S3 测试契约修订，并表示范围内选择自行处理。

**解释**：这是用户直接表达的注意力偏好，也是授权范围记录的正向例子。应复用已有批准，而非换阶段、换子代理或恢复上下文就再问一次。不能把这句话解释成所有未来范围变更均获批准。

R3 第 1490、1497、1690 行还表明，当时两项请求涉及冻结的验收契约与 SDK 改动，并已有调研和独立复核。因此不能把这两次请求一概定性为毫无必要；改进点是合并决策、解释具体变化，并在批准后延续执行。

### 2. 技术方案被拆成多轮确认，复杂度说明晚于推荐

**证据**：R2 第 324、345、357 行分别出现“需要你确认两个方案级选择”“继续前需要你确认两个边界”“还需要你确认最后两个方案选择”。时间为 09-03 23:41–23:56 +08，v0.7.2。

第 364 行，用户追问“2.这个详细和我说一下”；第 371 行才详细展开双层授权的签发、状态和集成要求。第 380 行，09-04 00:05:05 +08，用户反馈：“太麻烦了……不希望东西都还没有做完，限制先来一大堆”。

**解释**：用户主动调用 plan-bs，合理共创不能被取消。但可以自行调查的技术选择不应逐项转给用户；推荐影响架构的方案之前，需要说明实际复杂度、现有机制能否复用和实施代价。这里分析的是决策信息与交互顺序，不据此导出通用的权限取消规则。

### 3. “先确认 acceptance，再调查关键假设”的顺序需要调整

**证据**：R2 第 440 行，09-04 06:29:53 +08，v0.7.2：“请回复‘确认 acceptance’；我随后进入现状调查、上游代码解剖和真机关键假设 spike。”

**解释**：确认用户目标可以发生在技术调查之前；但涉及可行性、上游能力和实际运行方式的方案承诺，应先做会改变决策的调查或最小 spike，再提交最终 review。否则用户选择时尚未掌握决定性约束。这里不能推断整个会话此前完全没有调查；证据指向的是这次正式验收确认与后续关键验证的排序。

### 4. 真正影响交付范围的决定，应保留并形成决策简报

**证据**：R1 第 11394–11405 行，09-01 11:29–11:30 +08，v0.6.2。Agent 查明 S4 要求启动生产 Runtime，但构造 Runtime 必需的 authority 又被计划划给 S5、排除在 S4 外。

第 11394 行提供两个具体选择：纳入最小 S5 执行组合，或保持 S4 边界并延期真实运行链，同时说明推荐和验收影响。用户第 11400 行选择 A；第 11405 行承诺修订后自主实施。

**解释**：这类用户可感知的范围和验收取舍必须保留。优化不是消灭确认，而是让用户看到已验证事实、可行选项、推荐、代价以及当前工作受影响的部分；范围内普通实现选择则由 Agent 处理。

### 5. gate 内部环形依赖转嫁成用户批准

**证据**：T1 第 274–291 行，处于 09-03 收尾段、09-04 标题之前，具体时分不详，v0.7.2。日志记载新轮七场景通过后，旧轮未关闭阻塞 finalize；但 retire 又要求继任轮已经 SHIPPABLE。

第 285–290 行称其为“死锁”，随后要求用户提供批准原文 hash，通过 acknowledge 作废旧轮，由新轮承接；第 291 行明确旧账本和证据原样保留。

**解释**：这是流程工具状态承接的问题，不天然属于产品范围或风险决策。Agent 应诊断并准备最小恢复方案，不能让用户反复处理内部账本手续。

**本次边界**：该 gate 环形依赖属于另一个代码问题，本次没有修复。也没有证明当前所有条件下仍会触发。不能擅自 acknowledge、waive、删除旧轮或将缺失验证变为 PASS；需要另行复现、修复状态迁移并验证证据承接。

### 6. 执行顺序与文档分类也造成整批复验

**证据**：T1 第 55 行，09-03 执行段，v0.7.2：后台 record-run 期间，同一 run-dir 又执行其他写入，日志记录“不支持并发”，最终出现完整性链断裂。

第 305–307 行明确属于 09-04，v0.7.2：“先记录后 attest，文档改动被 fail-closed 判成行为变更，7 场景全部作废”，继而重新记录。

**解释**：应区分真实代码变化要求的复验与执行基础设施造成的重复劳动。操作前检查、写入串行化、变更影响分类和候选承接可减少无效重跑；但必须先证明旧证据仍适用于当前身份，不能直接复用不匹配的 PASS。

**本次边界**：并发写入损坏和 gate 重认证行为都没有在本次修复。规则优化仅要求按既有身份和影响范围规则恢复，不增加自动豁免或重开 run 清除失败的出口。

### 7. 技术进展需要持续对应用户可用能力

**证据**：R3 第 3771 行，09-05 10:50:26 +08，用户要求报告进度；第 3824 行，11:10:08，追问“那你的目标是什么呢？”；第 3856 行请求评估原 plan 的不合理处，均为 v0.7.2。

第 3901 行，Agent 总结：“底层越来越严密，用户真正能用的完整链路却很晚才得到验证。”第 3962 行改为先完成主对话和记忆闭环，并按“现在能实际做什么”汇报。

**解释**：进度应围绕当前可用行为、下一可展示结果及关键阻碍；测试条数和内部 gate 状态是支持证据。日志此前确实有大量进度更新，不能断言 Agent 没有汇报；问题是这些更新是否帮助用户判断目标达成，而非迫使用户再次追问目标。

### 8. 局部复测和独立推进已有正向实例

**证据**：R3 第 2206 行，09-05 09:24:25 +08：“不重复运行已通过的大套件”；第 2752 行，09:55:28：“修复这两项，不重做无关测试；旧证据保留原样”。

第 3167 行，10:14:36，Provider 传输中断、结果未知后，Agent 停止该轮隔离进程，避免重复发送，并让“其他可独立完成的工作继续”。均为 v0.7.2。

**解释**：这一行为适合固化为默认规则：暂停真正依赖阻塞的部分；已授权独立任务继续；复测围绕变更和失败根因；未知外部副作用不得盲目重发。以上是历史行为证据，不证明本次改动后的模型必然遵守。

## 既有 v0.7 能力与本次改动的区别

当前基线提交历史显示，v0.7.0 已将机器 gate 降为 opt-in、默认 journal 收尾；v0.7.2 已加入独立代码 review 和修复后的分层复验。这些不是本次新增成果，也不应把遗留机器账本的成本直接概括为当前所有默认流程的成本。

然而 R2、R3 的事件发生在本机激活 v0.7.2 之后，仍出现重复确认、决策信息后补和用户重申目标。说明只调整门禁或增加审查不足以统一各入口的交互语义。本次针对的是用户授权延续、调研与决策的先后顺序、范围内修复的自主执行、等待期间的独立推进，以及用户可理解的进度。
